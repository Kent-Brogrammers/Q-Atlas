# Neutrino simulation in the compiler

Updated on top of Chris's `main` revision `30d684e`.

1. Open **Python Compiler**.
2. Choose **Neutrino simulation · matter resonance**, then **Load example**.
3. Select **Convert Python**. The compiler validates the declaration and generates
   a standalone SciPy/Qiskit comparison script and the exact layer-rotation circuit.
4. Choose **On this computer**, then **Run neutrino comparison**.
5. Results show classical, ideal circuit and finite-shot conversion probabilities,
   per-point timings, summed timing scopes, and a downloadable raw JSON record.

Source: [neutrino_simulation.py](../examples/compiler/programs/neutrino_simulation.py).
Change its literal parameters, layers, samples or shots and convert again to run a
new experiment. The request/resource limits are identical to the Neutrino Lab.

This is an explicit **scientific declaration** marked `@qatlas.neutrino`, rather than
an arbitrary NumPy program or a binary optimization objective. The compiler reads
literal input data through an allowlisted AST; it never imports or executes submitted
Python. It generates circuits using the existing Neutrino Lab builder. Both the
export and runtime use the same curve-point inputs and effective simulator seeds.
QUBO/QAOA is not used for propagation. Existing `@qatlas.objective` examples retain
their original behavior.

The example uses electron flavor initially, theta=0.2, normalized splitting/energy=1,
distance=4.0336988686 and nine potentials from 0 to 1.842121988. The center lies at
resonance, with ideal complete conversion. Each point collects 1024 shots with its
recorded seed. This is the same two-flavor normalized model as the Lab, not a full
three-flavor or interacting-neutrino simulation.

## What the timing comparison means

- **Classical probability calculation:** SciPy's independent 2×2 Hamiltonian
  propagation and probability extraction, summed over the selected curve points.
- **Ideal circuit execution only:** Aer statevector execution, also summed over
  points. This interval is already included in the circuit workflow.
- **Circuit workflow on this computer:** circuit construction, transpilation,
  ideal statevector simulation, shot sampling and count extraction. It performs
  extra work relative to exact probability calculation.

These timers exclude source conversion, HTTP/browser waiting, numerical stability
checks and process startup outside the measured work. They are single-run measurements,
not a repeated runtime study. All local quantum results are classical simulation,
and no practical quantum speedup is implied. A one-qubit model is classically easy.

The downloaded script embeds the validated point inputs and QASM generated by the
Lab builder. It independently calculates the SciPy reference and runs each compiled
circuit locally. It has its own measured timers; loading embedded QASM differs from
building the circuit in the API, so its wall-clock values need not match the API.

For physical execution, choose **On an IBM quantum computer** and inspect the effective
request before submitting. Existing hardware bounds apply (128 shots per circuit,
small curves and a 10-second reservation). Original saved results keep their original
inputs; a saved three-point demo is not a newly measured nine-point curve. Physical
usage/queue/network scopes remain separate from local computation. Page loading,
source conversion and local Run submit no physical job.

Additive API endpoints:

- `POST /api/compiler/neutrinos/generate` with `{ "source": "..." }`.
- `POST /api/compiler/neutrinos/benchmark` with the same source; returns the existing
  `NeutrinoResponse`. It uses the Lab's existing bounded worker and failure handling.
